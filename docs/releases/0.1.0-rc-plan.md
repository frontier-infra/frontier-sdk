# Frontier Foundation 0.1.0-rc plan

Status: executable release-preservation plan  
Release identifier: `frontier-foundation-0.1.0-rc.1`  
Publication: prohibited in this milestone

The release identifier labels the Foundation assembly. It does not rewrite the
intrinsic package versions: protocol remains `0.1.0`, audit remains `0.1.2`, and
the four previously unpublished packages remain `0.1.0` until a publication
milestone explicitly versions and publishes them.

## Outcome

Turn the accepted, proposal-only Frontier foundation vertical into committed,
rebuildable, CI-governed release-candidate source without adding product features,
publishing packages, or modifying the Rust `harnessd` engine.

## Scope locks

- No connector marketplace, Singer/Meltano runtime, SSO, multitenancy, commercial
  packaging, dashboard expansion, or new provider abstraction.
- No package publication, remote push, production deployment, or registry mutation.
- No rewrite or source modification in `conductor-harness`.
- Package tests establish library behavior only. They do not establish Machine-L3 or
  a live governed-effect deployment.

## Package decisions

### React package

Keep `@frontier-infra/governance-react` for the RC. It names the actual bounded
surface—contracts, approvals, receipts, health, quarantine, and override—and avoids
claiming ownership of every future Frontier React component. The shorter
`@frontier-infra/react` name is rejected for this RC because it is broader than the
implemented contract. No compatibility alias is created before publication.

### Adapter package

Keep one `@frontier-infra/adapters` package for `0.1.0-rc.1`. Its implementations are
dependency-injected reference ports with one shared contract suite; splitting them now
would multiply public version and compatibility surfaces before a live deployment has
validated those boundaries. The package must continue separating proposal-only worker
ports from opaque capability-gated effect execution. A later split requires deployment
evidence and a migration plan; it is not part of this RC.

## Execution sequence and gates

1. **Preserve source**
   - Create local `rc/0.1.0-rc.1` branches in SDK, plugin, and Journeyman repos.
   - Commit SDK packages and their package-level documentation in reviewable Lore commits.
   - Regenerate/check and commit plugin consumer snapshots separately.
   - Commit the bounded Journeyman vertical and corrected status documentation separately.
   - Gate: every product-bearing file is tracked in its canonical repository or classified above.

2. **Release automation**
   - Add one package manifest used by CI and dry-run tooling.
   - Add a dependency-free script that packs every supported JavaScript package without publishing,
     records SHA-256/size/name/version, and fails on missing or unexpected packages.
   - Add a single RC verification entry point covering Node, Python, typed consumer,
     chaos, audit snapshots, plugin consumer snapshots, and package packing.
   - Extend GitHub Actions to execute the same gates. Existing publication remains limited
     to packages explicitly enabled for publication; all new RC packages remain disabled.
   - Gate: local and CI commands share the same package manifest and cannot publish in dry-run mode.

3. **Rust conformance map**
   - Map public harness-kit semantics to evidence in the existing Rust engine by path,
     invariant, and gap.
   - Record stronger Rust behavior without moving it into TypeScript and record missing
     equivalence without weakening the public contract.
   - Gate: no file under `conductor-harness` is modified.

4. **Reproducibility and evidence**
   - Verify SDK and Journeyman from temporary clean checkouts with their documented sibling layout.
   - Run the RC verification entry point and repeat package assembly to confirm stable hashes.
   - Check Docker availability; record `UNVERIFIED` if the daemon remains unavailable.
   - Write the RC report with exact commits, artifacts, checksums, proven claims, and non-claims.
   - Gate: no dirty tracked source remains in the three RC repositories; any local artifact directory is ignored and reproducible.

## Required commands

The completed milestone must expose these stable entry points:

```bash
# SDK repository
npm run rc:verify
npm run rc:pack

# Journeyman product repository
cd product
npm ci
npm run verify
```

`npm run rc:pack` writes ignored artifacts and a machine-readable manifest beneath
`dist/frontier-foundation-0.1.0-rc.1/`. It must never invoke `npm publish`.
