# Frontier Foundation 0.1.0 launch checklist

Status: **publication prepared; publication not authorized or performed**

## Launch shape

The first public availability step uses npm's `next` distribution channel for
the four new packages. It does not promote them to `latest`:

- `@frontier-infra/harness-kit@0.1.0`
- `@frontier-infra/adapters@0.1.0`
- `@frontier-infra/governance-react@0.1.0`
- `@frontier-infra/create-frontier-app@0.1.0`

Protocol `0.1.0` and audit `0.1.2` already exist on npm and remain on `latest`.
They remain in the Foundation assembly and its compatibility tests, but are
explicitly excluded from this publication set. Their historical registry bytes
are not represented as newly verified RC artifacts and are never republished.

The only publishing trigger for this assembly is the exact annotated tag
`foundation-v0.1.0-rc.1`. Manual workflow dispatch remains verification-only.

## Proven before publication

- The protected draft PR reconstructs the Foundation from pinned repositories.
- Node, Python, strict packed TypeScript, neutral second-consumer, chaos, browser,
  snapshot, and reproducible-package gates pass on GitHub-hosted Linux.
- The hosted artifact binds a clean source commit and records
  `publication_performed: false`.
- The package list is manifest-derived. Every enabled package requires an
  explicit npm distribution tag.
- The starter installs and builds from the exact local tarball chain without a
  registry dependency.

## Operator-controlled prerequisites

An npm trusted publisher can only be attached after a package exists. The first
publication therefore needs one tightly bounded bootstrap credential. This
follows npm's [trusted publishing](https://docs.npmjs.com/trusted-publishers/)
and [provenance](https://docs.npmjs.com/generating-provenance-statements/)
requirements:

1. Create a short-lived granular npm token scoped to the four new package names,
   with publish access and the minimum 2FA bypass needed for non-interactive CI.
2. Store it only as the `NPM_TOKEN` secret in the protected `npm-next` GitHub
   environment.
3. Use the exact release tag once. The hosted workflow publishes the already
   verified tarballs with provenance to `next`.
4. Delete the GitHub secret and revoke the npm token immediately after the
   first successful publication.

Never paste the bootstrap token into an issue, pull request, chat, log, or local
release document. Enter it directly into the protected GitHub environment.

Then configure npm trusted publishing for each new package:

| npm package | Repository | Workflow |
| --- | --- | --- |
| `@frontier-infra/harness-kit` | `frontier-infra/frontier-sdk` | `release.yml` |
| `@frontier-infra/adapters` | `frontier-infra/frontier-sdk` | `release.yml` |
| `@frontier-infra/governance-react` | `frontier-infra/frontier-sdk` | `release.yml` |
| `@frontier-infra/create-frontier-app` | `frontier-infra/frontier-sdk` | `release.yml` |

Each trusted publisher must allow `npm publish`. After verifying OIDC publishing,
set package publishing access to require 2FA and disallow traditional tokens.
No long-lived npm token belongs in GitHub, the repository, or a local agent
environment.

## Publication gate

Publication requires all of the following:

1. PR checks pass at the exact reviewed head.
2. The draft PR is reviewed and intentionally promoted to `main`.
3. For the first publication only, the bounded bootstrap token is installed in
   the protected `npm-next` environment and its revocation is assigned.
4. Jason explicitly authorizes creation of `foundation-v0.1.0-rc.1`.
5. The release workflow verifies the exact tag and artifact bytes before any
   publish command.
6. Trusted publishers are configured and the bootstrap credential is removed
   immediately after the new package pages exist.

## After publication

Run from a clean directory:

```sh
npx @frontier-infra/create-frontier-app@next my-frontier-app
cd my-frontier-app
npm install
npm run build
```

Record the resolved package versions, npm integrity values, provenance links,
generated app build result, and any registry propagation delay. The workflow
preserves a registry evidence artifact containing each version, distribution
tag, integrity value, and shasum. If publication stops after only some packages
exist, do not unpublish or overwrite them: keep the halt in place, inspect the
evidence, correct the failing package, and rerun the same idempotent workflow.
A failed smoke test likewise requires a new fix-forward version.

npm performs publish-time malware scanning before a new package becomes
installable. The workflow polls the public registry for up to 20 minutes before
running its npm-hosted smoke test; an accepted publish followed by a temporary
404 is not treated as proof that publication failed.

Promotion from `next` to `latest` is a later decision. It requires an
independently maintained consumer run against npm-hosted packages and does not
follow automatically from publication.
